# 변경을 격리하는 모듈과 조립

새 기능이 들어올 때 완료된 모듈의 내부를 다시 수정하는 일을 줄인다. 모듈은 한 가지 책임과 한 가지 주된 변경 이유를 갖고, 호스트는 필요한 부품을 선택해 연결하는 얇은 코드로 유지한다. 기존 코드 수정을 금지하는 규칙은 아니다. 요구나 계약이 실제로 바뀌면 해당 소유 모듈을 명확히 수정한다.

## 설계 전 판단

1. 지금 요구와 가까운 후속 변경 2~3가지를 적고, 각각 어느 파일이 바뀌어야 하는지 예측한다. 제품별 차이, 실행 환경 차이, UI 표현, 제어 정책, 물리 I/O를 구분한다.
2. 함께 바뀌는 데이터와 정책은 한 모듈 안에 둔다. 변경 이유가 다른 것은 좁은 계약으로 연결한다. 디렉터리 이름이나 클래스 수보다 실제 수정 파급 범위가 판단 기준이다.
3. 공통화는 두 곳 이상에서 같은 **의미와 규칙**을 사용할 때 우선한다. 단순히 코드가 닮았다는 이유로 제품별 정책을 공통 모듈에 합치지 않는다. 첫 사용 사례만 있는 추측성 범용 계층은 만들지 않는다.
4. 플랫폼별로 달라지는 입력·출력에서만 작은 port를 둔다. 기존 계약과 `Board` 공개 facade를 먼저 확인한다. UI와 제품 정책은 공통 소스로 두고, Windows와 HMI 호스트는 생성·주입·수명·이벤트 루프만 조립한다.
5. 호스트의 분기와 설정이 늘어나면 제품별 설정/정책 객체나 작은 생성 함수를 고려한다. 단일 거대 `App`, 서비스 로케이터, 임의의 `void*` 저장소, 모든 기능을 가진 범용 인터페이스로 확장하지 않는다.

## 구현과 검토

- 모듈의 공개 계약에 입력, 출력, 소유권, 수명, 오류 결과를 드러낸다. 구현 세부사항과 플랫폼 헤더가 공통 계약으로 새지 않게 한다.
- 새 변형을 추가할 때 기존 핵심 모듈의 수정 대신 새 구현과 조립 변경으로 끝나는지 검토한다. 기존 모듈 수정이 필요한 경우 그 이유를 기록하고, 반복될 변화라면 경계를 조정한다.
- 공통 상태/정책을 Windows와 HMI에서 별도로 복제하지 않는다. 가상 장치와 실제 장치는 동일한 정책에 서로 다른 입력·출력을 제공한다.
- 계약 검증은 경계에서 의미 있는 사례만 테스트한다. 구현을 그대로 따라 쓰는 테스트나 파일 배치만 검사하는 테스트를 늘리지 않는다.
- 임베디드에서는 추상화 비용을 확인한다. 객체 크기, 정적/힙/스택 할당, 복사 횟수, 시작 순서를 검토하고 불필요한 동적 다형성은 피한다.

## 작업 결과에 남길 것

계획이나 변경 설명에는 모듈별 책임과 변경 이유, 호스트가 조립하는 지점, 예상되는 다음 변형의 수정 파일을 간단히 적는다. 검증에서는 새 변형 추가가 공통 정책 복제나 기존 모듈의 광범위한 수정을 요구하지 않는지 확인한다.

UI와 플랫폼을 함께 다룰 때는 `cross-platform-ui-development`, `Board`와 그 호출자를 다룰 때는 `board-boundary-guard`, C/C++ 모델·시작 경로·콜백의 메모리 사용을 바꿀 때는 `embedded-memory-safety`도 적용한다.
